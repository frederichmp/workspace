**Ordem em `registrar_decisao_kill`:**
1. Validar decisão; `instante_decisao = agora()`; aprovador vazio → REJEITADO/SEM_IDENTIFICACAO; TTL vencido → TIMEOUT/APROVACAO_EXPIRADA (como hoje).
2. Não APROVADO → registro único `fase="RESULTADO"` e retorno.
3. APROVADO → `id_intervencao = uuid4().hex`; gravar **INTENCAO** (`decisao=APROVADO`, `resultado_banco=null`) com `flush` + `os.fsync` **antes** de `executar_kill_verificado` (portanto antes da reconsulta DIAG). Qualquer exceção → `FALHA_LOG_APROVACAO`: sem DIAG, sem KILL, sem e-mail.
4. `executar_kill_verificado(..., preparado_em, agora)`: reconsulta DIAG → hash → elegibilidade → **segundo recheck de TTL** (reusa `_aprovacao_expirada`; vencido → `resultado_banco="APROVACAO_EXPIRADA"`, sem KILL) → `matar_sessao_oracle`. Exceção genérica → `resultado_banco="ERRO_INTERNO"`, `executado=False`.
5. Gravar **RESULTADO** (fsync, mesmo `id_intervencao`); `logger.log`; e-mail; retorno.

**Formato:** JSONL único, append-only; campos novos `fase` (obrigatório, validado) e `id_intervencao` em todos os registros. APROVADO = 2 linhas; REJEITADO/TIMEOUT = 1 linha `RESULTADO`. Regra do auditor: INTENCAO sem RESULTADO com o mesmo id = desfecho desconhecido → conferir `OPS_KILL_AUDIT`.

**Falhas de escrita** (retorno ganha `falha_registro`: `None` | `"INTENCAO"` | `"RESULTADO"`):

## 9. Bytes dos scripts homologados preservados (achado novo CRLF/hash)
Decisão: responsável (forma) e `seguranca` (detalhes). Implementação: sessão principal, porque `.gitattributes` toca a integridade dos bytes verificados por hash. Testes: `mecanico`.
- **`.gitattributes` (decisão do responsável):**
  ```
  # Scripts SQL sempre em LF no disco e no repositório: o hash de registry/ é calculado sobre esses bytes.
  *.sql text eol=lf
  ```
- **Hash sobre os bytes do repositório:** o cálculo continua sobre os bytes lidos do disco, **sem normalizar CRLF→LF** (`executor.py:653-681` calcula o hash sobre `bytes_brutos` e executa esses mesmos bytes). Com `eol=lf`, os bytes do disco num checkout são os bytes do blob. `executor.py`, `registry.py`, `verificar_registro.py` e `registry/` ficam intocados.
- **Estado medido (`git ls-files --eol -- '*.sql'`):**
  - todos os blobs `.sql` já são LF ou não têm fim de linha (`i/lf` ou `i/none`), então **nenhum blob muda e nenhum hash muda**;
  - 13 arquivos estão com CRLF no disco (`db/ops_kill.sql` e 12 de `tests/corpus_adversarial`). Depois do commit, regravá-los a partir do blob com `git checkout -- <13 caminhos>`, sem perda, porque o conteúdo normalizado é idêntico ao blob.
- **Risco residual apontado pelo `seguranca`, aceito pelo responsável:**
  - O problema: com `eol=lf`, quem salvar um script em CRLF e recalcular o hash sobre o disco local registraria um hash que não bate com o blob LF.
